# Интерактивная карта торгового центра — прототип 2D/3D

Интерактивный прототип карты торгового центра, построенный на **чистом JavaScript (ES6+)**
и **Three.js**. При запуске он генерирует торговый центр на 100 помещений, раскладывает
помещения на сеточный план без пересечений и отображает результат либо в изометрическом
3D-виде, либо в виде плоского 2D-архитектурного плана — с плавной анимированной
транзицией между ними, подсветкой при наведении и выбором по клику.

Реализовано в соответствии с **Техническим заданием v1.3**.

> **Живая демонстрация:** <https://unrealalexstar.github.io/interactive-mall-map/>

> **Фронтенд-фреймворк не используется.** В проекте нет React, Vue, Angular или
> Svelte — каждый элемент управления, каждый DOM-узел и вся 3D-оркестрация
> представляют собой обычные ES-модули и обычный CSS. Единственная runtime-зависимость —
> `three`; единственная зависимость сборки — `vite`.

## Обзор архитектуры

Приложение организовано как набор **однонаправленных модулей с единственной
ответственностью**. Ни один модуль не лезет в внутренности другого: они общаются через
обычные вызовы методов и через данные, которые передаёт им `main.js`.

```
                 ┌──────────────┐
                 │   data.js    │  generateShopData(100)
                 │  (чистый)    │  → ShopData[]
                 └──────┬───────┘
                        │ ShopData[]
                 ┌──────▼───────┐
                 │   layout.js  │  layoutShops(shops, opts)
                 │  (чистый)    │  → { placements[], bounds, stats }
                 └──────┬───────┘
                        │ placements[]
        ┌───────────────┼────────────────┬──────────────────┐
        │               │                │                  │
 ┌──────▼──────┐ ┌──────▼──────┐  ┌──────▼──────┐  ┌────────▼────────┐
 │   scene.js  │ │  labels.js  │  │ camera.js   │  │ interaction.js  │
 │ меши+пол    │ │ подписи 2D  │  │ камеры+твин │  │ рейкаст/выбор    │
 └──────┬──────┘ └──────┬──────┘  └──────┬──────┘  └────────┬────────┘
        │               │                │                  │
        └───────────────┴────────────────┴──────────────────┘
                                │
                        ┌───────▼───────┐
                        │    main.js    │  связывает всё, UI, цикл RAF
                        └───────────────┘
```

### Ответственность модулей

| Модуль | Ответственность | Чего он **не** делает |
| --- | --- | --- |
| `data.js` | Создаёт `ShopData[]` из seed. Чистый, детерминированный, без DOM. | Ничего не знает о Three.js или DOM. |
| `layout.js` | Превращает `ShopData[]` в непересекающиеся координаты `(x, z)`. Чистый. | Не создаёт геометрию. |
| `scene.js` | Создаёт рендерер, пол, свет и меши магазинов. | Не знает о камере или указателе. |
| `labels.js` | Владеет спрайтами подписей, их `CanvasTexture` и адаптивным масштабированием. | Не знает об алгоритме компоновки. |
| `camera.js` | Владеет обеими камерами, орбитальным управлением и анимацией 2D/3D. | Не трогает содержимое сцены. |
| `interaction.js` | Рейкастинг, состояние наведения, состояние выбора и их визуализация. | Не двигает камеру. |
| `main.js` | Компонует модули, связывает UI, запускает цикл RAF. | Не реализует никаких алгоритмов. |

### Поток данных во время работы

1. **Запуск** — `main.js` генерирует данные и компоновку, затем создаёт сцену,
   подписи, камеру и менеджер взаимодействия.
2. **Кадр** — `requestAnimationFrame` задаёт фиксированный порядок операций:

   ```js
   cameraManager.update(now);        // продвигаем анимацию / орбитальное управление
   interaction.update();             // обновляем наведение (максимум 1 рейкаст за кадр)
   labels.setBlend(cameraManager.blend);   // двигаем якоря подписей между 2D и 3D
   labels.update(camera, height);    // пересчитываем масштаб и позиции (если камера двигалась)
   if (cameraChanged || hoverChanged || labelsChanged || needsRender) {
     renderer.render(scene, camera);       // проход WebGL
     labels.render(renderer);              // подписи поверх, тот же WebGL-буфер
   }
   resolutionScaler.update(delta);   // снижаем разрешение, если кадры стали медленными
   ```

   Порядок важен: камера должна быть окончательно установлена *до* того, как
   менеджер взаимодействия сделает по ней рейкаст, а подписи должны быть
   пересчитаны до отрисовки, чтобы их экранные прямоугольники совпадали с
   текущим кадром. `labels.render()` обязателен после основного прохода: он
   очищает цветовой буфер, поэтому подписи рисуются заново в каждом
   отрисованном кадре. Если изменений нет, не выполняется ни один из проходов.
3. **События** — события указателя обновляют менеджер взаимодействия, который
   передаёт изменения состояния обратно через колбэки (`onHover`, `onSelect`),
   чтобы `main.js` мог обновить DOM-панели, при этом модули никогда не обращаются
   друг к другу напрямую.

### Зачем такое разделение

* `data.js` и `layout.js` — **чистые функции над простыми объектами**. Их можно
  покрыть юнит-тестами в Node без DOM и WebGL — см. `scripts/verify-layout.mjs`.
* `scene.js`, `labels.js` и `camera.js` владеют ровно одной подсистемой Three.js
  каждый, поэтому замена подсистемы подписей (DOM → canvas → спрайты) или камеры
  не затрагивает остальное приложение.
* `interaction.js` — единственный модуль, работающий с указателем, что делает
  слой ввода тривиально заменяемым (touch, геймпад, пульт).

## Алгоритм компоновки

**Файл:** `src/layout.js` · **Точка входа:** `layoutShops(shops, { padding, aisle, cell })`

План этажа — это двумерная задача упаковки: каждое помещение представляет собой
прямоугольник `width × depth`, выровненный по осям, который нужно разместить на
плоскости XZ так, чтобы никакие два прямоугольника не пересекались. Алгоритм —
классическая **упаковка полками** (она же *level packing*), расширенная проходом
автоматического подбора ширины полки.

### 1. Модель

Помещения группируются в горизонтальные **полки** (ряды). Каждая полка — это полоса
постоянной глубины:

```
   проход
   ├───────┐
   │ пом. A│ │ пом. B│ │ пом. C│ │  пом. D  │      <- глубина полки = глубина
   │       │ │       │ │       │ │          │         первого помещения на ней
   ├───────┴─┴───────┴─┴───────┴─┴──────────┤
   ├───────┐                                ┤
   │ пом. E│ │ пом. F│                     │      <- следующая полка
   ├───────┴─┴───────┴────────────────────┤
   <--------- предел ширины полки --------->
```

* **`padding`** — зазор между двумя помещениями, стоящими рядом на *одной* полке
  (по умолчанию `1` мировая единица).
* **`aisle`** — проход между двумя соседними полками (по умолчанию `2` мировые
  единицы). Именно благодаря ему результат читается как план этажа, а не как
  сплошной блок геометрии.
* **`cell`** — разрешение сетки плана (по умолчанию `1` мировая единица).

### 2. Сортировка — Next Fit Decreasing Height (NFDH)

```
sorted = units.sort(by depth DESC, then width DESC, then id ASC)
```

Сортировка по наибольшему измерению в первую очередь делает упаковку полками
эффективной: **первое** помещение на полке задаёт глубину полосы, а поскольку список
отсортирован по убыванию глубины, каждое следующее помещение гарантированно
удовлетворяет условию `unit.depth ≤ shelf.depth`. Поэтому помещение никогда не может
выйти за пределы полосы.

### 3. Правило размещения

Помещение помещается на полку `S` **тогда и только тогда**, когда выполнены оба условия:

```
(a)  unit.depth  ≤ S.depth                      // полоса достаточно глубокая
(b)  S.cursor + unit.width ≤ shelfWidth         // полка достаточно длинная
```

`S.cursor` — это x-координата **левого края** следующего помещения, и она уже
включает хвостовой отступ предыдущего помещения:

```
leftEdge = S.cursor
center.x = leftEdge + unit.width / 2
S.cursor = leftEdge + unit.width + padding      // сдвиг за помещение + зазор
```

Первое помещение на полке начинается вплотную к началу полки, каждое следующее
отделено от левого соседа ровно на `padding`, а проверка в (b) автоматически
учитывает этот зазор, потому что курсор его содержит.

### 4. Открытие новой полки

Если ни одна полка не принимает помещение, открывается новая *ниже* предыдущего ряда:

```
shelf.z = previousShelf.z + previousShelf.depth + aisle
shelf.depth = unit.depth          // первое (самое глубокое) помещение задаёт полосу
```

Полоса полки — это `[z, z + depth]`. Помещения **выровнены по переднему краю**
(`unit.z = shelf.z + unit.depth / 2`), поэтому у всех помещений ряда общая линия
витрин — менее глубокие помещения просто оставляют зазор в глубине полосы.

### 5. Сеточный снимок (решётка)

Все входные данные целочисленные, а начало полки совпадает с началом координат,
поэтому:

* каждый **край** попадает на целую линию решётки,
* каждый **центр** попадает на кратное `0.5` (`edge + size / 2`).

Финальное смещение для центрирования — `(−width/2, −depth/2)`, что также кратно
`0.5`, поскольку размеры целочисленные, — так решётка сохраняется от начала до конца.
Финальное `Math.round(v * 2) / 2` убирает любые погрешности плавающей точки.

```
    z
    ↑
    │ ┌───┬───┬───┐   полка 0   (передний край z = 0)
    │ │ A │ B │ C │
    │ └───┴───┴───┘
    │  ← проход = 2 →
    │ ┌───┬───┐       полка 1   (передний край z = 0 + depth + aisle)
    │ │ D │ E │
    │ └───┴───┘
    └──────────────────→ x
```

### 6. Центрирование и автоподбор ширины полки

Единая ширина полки редко даёт хорошую форму этажа. Поэтому упаковщик
перезапускается для диапазона ширин-кандидатов вокруг идеального квадрата `√(totalArea)`:

```
for candidate in [0.55 · √A, 2.79 · √A] (step 0.08 · √A, 29 candidates):
    result  = packShelves(units, shelfWidth = candidate)
    area    = result.width · result.depth
    aspect  = ((result.width − result.depth) / max(result.width, result.depth))²
    score   = area · (1 + 0.6 · aspect)        // штраф за вытянутый план
keep the result with the lowest score
```

Мультипликативный штраф за пропорции заставляет упаковщик предпочитать **компактный
квадратный этаж** длинному коридорообразному, при этом слагаемое `area` по-прежнему
поощряет эффективную упаковку.

### 7. Результат

Для seed по умолчанию алгоритм выдаёт:

```
shelves        : 9
plan           : 67.00 x 64.00 units
shelf limit    : 67.77 units
occupancy      : 58.8 %        (sum of unit areas / plan area)
overlaps       : 0            (verified at runtime)
```

### 8. Проверка во время работы

В `layout.js` есть помощник `verifyLayout(placements)`, который выполняет
**O(n²)** проверку пересечений AABB (4 950 пар для 100 помещений — ничтожно мало)
и возвращает список нарушений. `main.js` вызывает её при запуске и пишет результат в лог:

```
[MALL MAP] Layout: 100 units · 9 shelves · 67.0 x 64.0 units · occupancy 58.8% · overlaps: 0
```

## Система камер 2D ⇄ 3D

**Файл:** `src/camera.js` · **Класс:** `CameraManager`

Рядом работают две камеры:

| | Режим 3D | Режим 2D |
| --- | --- | --- |
| Камера | `PerspectiveCamera` (fov 45°) | `OrthographicCamera` |
| Позиция | Изометрия: полярный угол 52°, азимут 40° | Строго над планом |
| Вектор up | `+Y` | `−Z` (север вверху экрана) |
| Управление | Орбита (вращение + панорама + приближение) | Только панорама + зум (`enableRotate = false`) |

### Почему переход бесшовный

Перспективная и ортографическая проекции **не** связаны жёстким преобразованием,
поэтому нельзя просто интерполировать «камеру A» в «камеру B». Решение здесь
состоит из трёх частей:

**1. Выразить 2D-состояние как перспективную позу.** 2D-кадрирование — это мировая
высота `H`, в которую должен поместиться план. Перспективная камера воспроизводит
ровно это кадрирование, когда стоит строго над планом на расстоянии `D`, где

```
H = 2 · D · tan(fov₂D / 2)          fov₂D = 30°
```

Затем ортографическая камера настраивается с `top = H/2`, `bottom = −H/2`,
`left/right = ±H·aspect/2` и `zoom = 1`. Поэтому оба рендера **попиксельно
идентичны** — проверочный тест утверждает `69.120000 vs 69.120000`.

**2. Интерполировать ориентацию через slerp кватернионов.** `Matrix4.lookAt()`
сохраняет ось `+Z` камеры вдоль `normalize(eye − target)`, поэтому весь переход
можно выразить так:

```
e        = easeInOutCubic(t)                    // кубический ease-in-out
target(t)= lerp(targetFrom, targetTo, e)
q(t)     = slerp(qFrom, qTo, e)
dir(t)   = q(t) · (0, 0, 1)                     // +Z камеры = от цели
pos(t)   = target(t) + dir(t) · lerp(radiusFrom, radiusTo, e)
fov(t)   = lerp(fovFrom, fovTo, e)
```

Это выражение воспроизводит начальную и конечную позу **точно**, потому что
`q · (0,0,1)` *и есть* `normalize(eye − target)`.

**3. Никогда не смешивать вектор up во время работы.** Вектор up меняется с `+Y`
(3D) на `−Z` (2D) — но он запекается в два кватерниона ориентации, а не
интерполируется. Смешивание его во время работы сделало бы направление взгляда и
вектор up параллельными в некоторой точке анимации, что вырождает `lookAt()`.
Запекание в кватернионы даёт естественное движение «камера наклоняется в вид
сверху» без сингулярности.

При `t = 1` менеджер переключает активную камеру. Поскольку оба кадрирования
идентичны, **переключение незаметно**.

Переход управляется меткой времени `requestAnimationFrame`, поэтому не зависит от
частоты кадров, а орбитальное управление отключается на время его выполнения.

### Кадрирование торгового центра

Обе камеры кадрируются по **ограничивающей сфере** плана — сфере радиуса
`bounds.radius` с центром в торговом центре. Подгонки сферы достаточно, чтобы
гарантировать, что каждый угол плана попадает в кадр, и это одна формула вместо
перебора восьми углов ограничивающего прямоугольника:

```
limit  = min(fov/2, atan(tan(fov/2) · aspect))   // более узкий половинный угол
radius = bounds.radius · 1.08 / sin(limit)        // расстояние до камеры
```

2D-план кадрируется так же, но по *высоте* плана, а не по сфере, потому что план
должен заполнить кадр точно.

## Подписи

**Файл:** `src/labels.js` · **Класс:** `LabelManager`

Подписи — это `THREE.Sprite` с собственной `CanvasTexture`. Текст растрируется
**один раз** при изменении содержимого, а на кадре остаётся только сдвинуть и
масштабировать готовые квады. Спрайты живут в отдельной сцене с ортографической
камерой в CSS-пикселях и рисуются вторым проходом поверх основной сцены
(`renderer.autoClear = false`), поэтому их экранные координаты напрямую совпадают
с координатами мыши.

Почему не DOM (`CSS2DRenderer`) и не отдельный полноэкранный `<canvas>`:
100 DOM-узлов заставляют браузер каждый кадр пересчитывать стили и композитить
слои, а прозрачный canvas размером с окно (при DPR 2 — 3200×2000) приходится
очищать, перерисовывать и заново композитить поверх WebGL. В обоих случаях
основная стоимость приходилась на браузер, а не на текст. Спрайты убирают и DOM,
и полноэкранный прозрачный слой: остаётся ~100 маленьких квадов в общем
WebGL-проходе.

### Текстура на подпись

Для каждой подписи создаётся offscreen-canvas, который запекается в
`CanvasTexture`:

```js
const texture = new THREE.CanvasTexture(canvas);
texture.colorSpace = THREE.SRGBColorSpace;
texture.minFilter = texture.magFilter = THREE.LinearFilter;
texture.generateMipmaps = false;

const material = new THREE.SpriteMaterial({
  map: texture,
  transparent: true,
  depthTest: false,
  depthWrite: false,
  sizeAttenuation: false,   // размер задаётся в пикселях экрана
  toneMapped: false
});
```

Текстура рисуется в максимальном масштабе (`dpr × 1.3`) и выводится на экран
уменьшенной, поэтому изменение масштаба при зуме не требует повторного
растеризования текста. Перерисовка происходит только когда меняется текст, LOD,
наведение или DPR — в обычном кадре цикл лишь сравнивает ключи кэша. Если текст
или LOD изменили размер canvas, текстура освобождается (`texture.dispose()`):
three.js выделяет GPU-память один раз, и без пересоздания обновление через
`texSubImage2D` не помещается в старое хранилище.

### Адаптивное поведение

При изменении матриц камеры менеджер проецирует якоря и вычисляет проецируемый
размер (в пикселях) застройки каждого помещения:

```
footprintPx = unitSize / unitsPerPixel            // размер помещения на экране
scale       = clamp(footprintPx / 30, 0.75, 1.3)  // адаптивный масштаб
space       = (footprintPx · 1.2) / scale - 14     // ширина макета для текста
```

* **Масштаб** — текст подписи всегда остаётся в диапазоне **9–15.6 px** на экране
  при любом уровне зума, поэтому никогда не становится нечитаемым.
* **Ширина** — подпись никогда не шире своего помещения на экране. Подписи
  выстраиваются рядом, а не накрывают соседей.
* **Обрезка** — количество помещающихся символов решается **в JavaScript**
  (`fitText()` в `src/labels.js`) с помощью `canvas.measureText()` для измерения
  реальной ширины текста. Имя обрезается, добавляется многоточие, а ширина
  текстуры задаётся ровно равной измеренной ширине текста.
* **Якоря** — якорь подписи интерполируется между «парит над коробкой» (3D) и
  «по центру застройки» (2D) с тем же значением `blend`, которое управляет анимацией
  камеры, поэтому подписи плавно следуют за камерой.

### Отрисовка только при изменениях

`main.js` не рисует кадр, если ничего не изменилось. Для подписей это означает:

* `cameraChanged()` сравнивает `matrixWorld` и `projectionMatrix` камеры со
  снимком предыдущего кадра. Снимки хранятся в `Float64Array`, а сравнение идёт
  с небольшим допуском: иначе шум вычислений матриц включал бы перерисовку
  вхолостую.
* Если камера не двигалась, `_project()` не вызывается вообще; `update()`
  возвращает `false`, и основной цикл пропускает `renderer.render()`.
* На неподвижной сцене не тратятся ни CPU, ни GPU, а картинка не мерцает от
  бесконечной перерисовки.

### Уровень детализации (LOD)

Подписи помещений шириной всего в несколько пикселей скрываются
(`sprite.visible = false`) — это порог, при котором текст перестаёт нести какую-либо
информацию. На практике в видах по умолчанию подписаны все 100 помещений, и LOD
включается только при сильном отдалении.

### Попадание мышью

Так как подписи больше не являются DOM-элементами, `pick(clientX, clientY)`
обходит сохранённые экранные прямоугольники в обратном порядке (последняя
нарисованная подпись — сверху) и возвращает `id` магазина. `InteractionManager`
вызывает этот метод до рейкаста по коробкам.

## Взаимодействие

**Файл:** `src/interaction.js` · **Класс:** `InteractionManager`

### Наведение

`pointermove` только сохраняет нормализованные координаты устройства и поднимает
флаг «грязно»; фактический рейкаст выполняется **не чаще одного раза за кадр** в
`update()`. Поэтому стоимость — `O(1)` за кадр, пока мышь движется, и ноль, пока
она неподвижна.

Наведённое помещение подсвечивается осветлением цвета к белому и включением
цветного эмиссивного свечения:

```js
mesh.material.color.copy(baseColor).lerp(WHITE, 0.34);
mesh.material.emissive.copy(baseColor);
mesh.material.emissiveIntensity = 0.5;
```

Поскольку в 2D-плане подписи лежат прямо поверх своего помещения, указатель может
оказываться над подписью, а не над мешем. Поэтому перед рейкастом вызывается
`labels.pick()`, который определяет магазин по сохранённым экранным
прямоугольникам; результат передаётся в ту же точку входа
`InteractionManager.setHover()`, чтобы подсветка и информационная панель
оставались синхронными независимо от того, что именно под курсором.

### Выбор

`pointerdown` выбирает сразу (чтобы обратная связь была мгновенной) и пишет
помещение в консоль браузера:

```js
console.log(
  `%c[MALL MAP]%c Shop selected  →  id: shop_043  |  name: Velvet & Co.  |  world position: (10.50, 1.00, -28.00)`,
  'background:#4dabf7;color:#0b0e14;padding:2px 6px;border-radius:3px;font-weight:700;',
  'color:#e9ecef;'
);
console.log({ id, name, category, width, depth, position: { x, y, z } });
```

Выбранное помещение отмечается:

* **контуром в виде инвертированной оболочки** — копией коробки, увеличенной до
  107 % по ширине/глубине (112 % по высоте) и отрисованной с `BackSide`, что даёт
  чистую рамку без постобработочного `OutlinePass`;
* **рамкой застройки**, нарисованной на плоскости пола;
* сильным эмиссивным свечением и осветлённым цветом;
* живой информационной панелью в углу экрана.

> Орбитальное управление слушает **общий контейнер**, а не canvas: контейнер
> занимает всё окно и остаётся стабильной целью, даже если canvas пересоздадут
> или поверх него появятся другие элементы интерфейса.

## Вопрос 1 — оптимизация подписей для 1000+ объектов

> Актуальная реализация уже заменила `CSS2DRenderer` на спрайты с
> `CanvasTexture` (см. [Подписи](#подписи)). Ниже — почему DOM не масштабируется
> до тысяч и какие шаги остаются, если подписей станет 1000+.

`CSS2DRenderer` был правильным выбором для прототипа со ~100 помещениями, но он
**не** масштабируется до тысяч. Каждая подпись — реальный DOM-узел, а рендерер
выполняет для каждого кадра и каждой подписи: умножение матриц, проекцию, запись
`style.transform`, запись `z-index` и запись `style.display`. Вдобавок браузеру
приходится композить, стилизовать и отрисовывать 1000 абсолютно позиционированных
элементов — пересчёт стилей и раскладка становятся узким местом задолго до WebGL.

### Где `CSS2DRenderer` перестаёт справляться

| Ограничение | Последствие при 1000+ подписях |
| --- | --- |
| Один DOM-узел на подпись | 1000+ элементов → пересчёт стилей + отрисовка доминируют в кадре |
| `style.transform` пишется каждый кадр | Заставляет композитор перерастеризовать каждую подпись |
| Сортировка по `z-index` | `CSS2DRenderer.sortObjects` сортирует все подписи каждый кадр (`O(n log n)`) |
| Нет встроенного LOD / устранения наложений | Все подписи позиционируются, даже если они шириной 1 px |
| Отрисовка текста | Браузер растеризует глифы при каждом изменении масштаба |

### Стратегии в порядке влияния

#### 1. Вынести текст из DOM — проекция на Canvas 2D

Отрисовать каждую подпись в один `<canvas>`-оверлей и нарисовать строки
самостоятельно. Это убирает 1000 DOM-узлов и заменяет их одним canvas и одним
циклом `fillText`. Проекция — та же математика, которую `CSS2DRenderer` выполняет
внутри:

```js
const _v = new THREE.Vector3();

function drawLabels(ctx, scene, camera, items, width, height) {
  ctx.clearRect(0, 0, width, height);
  const viewProjection = new THREE.Matrix4()
    .multiplyMatrices(camera.projectionMatrix, camera.matrixWorldInverse);

  for (const item of items) {
    item.object.getWorldPosition(_v);            // мировая позиция якоря
    _v.applyMatrix4(viewProjection);              // -> clip space

    if (_v.z < -1 || _v.z > 1) continue;          // за камерой / отсечено

    const x = (_v.x * 0.5 + 0.5) * width;         // NDC -> экран
    const y = (-_v.y * 0.5 + 0.5) * height;

    ctx.save();
    ctx.font = `${item.fontSize}px "Inter", system-ui, sans-serif`;
    ctx.textAlign = 'center';
    ctx.textBaseline = 'middle';
    ctx.fillStyle = item.color;
    ctx.fillText(item.text, x, y);                // один draw call для текста
    ctx.restore();
  }
}
```

**Стоимость:** один `fillText` на видимую подпись, один canvas, ноль DOM.
Растеризация глифов кэшируется браузером для каждой пары (шрифт, размер).

**Дальнейшая оптимизация:** предварительно отрисовать каждую подпись **один раз**
в offscreen-canvas и использовать `drawImage()` — или, лучше, запечь все подписи в
единый **текстурный атлас** (см. ниже) и рисовать один квад на подпись через
`drawImage` из атласа. `drawImage` из кэшированного битмапа намного дешевле, чем
`fillText`.

**Компромисс:** вы теряете CSS-оформление, выделение текста и доступность. Для
canvas-карты это обычно правильный компромисс.

#### 2. Текстурный атлас + инстансированные квады (путь через GPU)

Запечь каждую подпись в единый текстурный атлас (например, 2048×2048, 1024 слота
по 64×64 или 128×32 px), затем рисовать подписи **одним инстансированным draw call**:

```js
// Один InstancedMesh из квадов, один инстанс на подпись.
const geometry = new THREE.InstancedBufferGeometry();
geometry.index = quad.index;
geometry.attributes.position = quad.attributes.position;
geometry.attributes.uv = quad.attributes.uv;

geometry.setAttribute('aOffset', new THREE.InstancedBufferAttribute(offsets, 3));
geometry.setAttribute('aScale', new THREE.InstancedBufferAttribute(scales, 2));
geometry.setAttribute('aUvOffset', new THREE.InstancedBufferAttribute(uvOffsets, 2));

const material = new THREE.ShaderMaterial({
  uniforms: { map: { value: atlasTexture } },
  vertexShader: /* gl_Position = projectionMatrix * modelViewMatrix * vec4(aOffset,1.0) ... */
});
```

**Стоимость:** 1 draw call на 1000 подписей, 1 привязка текстуры, никаких
переключений состояния на подпись. Позиции подписей обновляются записью в массивы
`InstancedBufferAttribute` и установкой `needsUpdate = true` — одна загрузка
буфера за кадр.

#### 3. Инстансированные спрайты (`THREE.Sprite` / `InstancedMesh`)

Если каждой подписи нужна собственная текстура (а не общий атлас), используйте
один `Sprite` на подпись с `SpriteMaterial` — по-прежнему без DOM, но это стоит
один draw call на подпись, если не использовать `BatchedMesh` (three r15x+),
который объединяет спрайты с общим материалом в один инстансированный draw call.

#### 4. Уровень детализации (LOD) и устранение наложений

Это самый большой **перцептивный** выигрыш, и он сочетается со всем перечисленным
выше:

* **Дистанционный LOD** — ниже порога заменить текст цветной точкой
  (квад из 2 треугольников) или вообще убрать подпись. В текущей реализации порог
  LOD — `footprintPx < 9`, то есть только когда помещение буквально в несколько
  пикселей шириной.
* **Ранжирование по важности** — отсортировать помещения по площади и при
  отдалении оставлять подписи *N* самых больших; остальные показывать постепенно
  по мере приближения камеры. Это сохраняет читаемость карты при любом зуме.
* **Разрешение перекрытий / окклюзий** — дешёвый жадный проход: отсортировать
  подписи-кандидаты по важности, пройти по ним и пропустить подпись, чей экранный
  прямоугольник пересекается с уже размещённым. При 1000 подписях это `O(n log n)`
  по экранным прямоугольникам, и это убирает большую часть визуального шума.

#### 5. Отсечение по пирамиде видимости — и оговорка про `CSS2DRenderer`

Three.js отсекает объекты за вас: `Object3D.frustumCulled` использует
ограничивающую сферу объекта против пирамиды видимости камеры, поэтому
внеэкранные меши ничего не стоят. **`CSS2DRenderer` делает то же для своих
подписей** — он вычисляет `_vector.z` и устанавливает `element.style.display = 'none'`
для подписей вне пирамиды, — но *DOM-узел всё равно существует*, и работа с
матрицами для каждой подписи всё равно выполняется каждый кадр. Экономия — только
на отрисовке, не на CPU.

Настоящая проблема в том, что у `CSS2DRenderer` **нет способа пропустить работу**:
нет хука «обрабатывать только подписи, чья ограничивающая сфера на экране», и нет
LOD на подпись. Смягчить это можно так:

* сгруппировать подписи в `THREE.Group` по этажу / по району и переключать
  `group.visible` — тогда рендерер пропускает всё поддерево
  (`renderObject` делает ранний выход при `object.visible === false` и вызывает
  `hideObject` для детей);
* самостоятельно предфильтровать подписи в `update()` и ставить
  `object.visible = false` для ненужных (именно это делает текущая реализация);
* вообще не использовать `CSS2DRenderer` сверх нескольких сотен подписей.

### Рекомендуемый план для 1000+ текстурированных объектов

| № | Техника | Выигрыш |
| --- | --- | --- |
| 1 | Заменить `CSS2DRenderer` на canvas-2D оверлей (`vector.project()`) | Убирает 1000 DOM-узлов → самый большой выигрыш |
| 2 | Предварительно отрисовать строки в атлас и использовать `drawImage` | Убирает растеризацию глифов каждый кадр |
| 3 | Запечь атлас в `InstancedMesh` со смещениями на инстанс | 1 draw call на все подписи |
| 4 | Дистанционный LOD + устранение наложений по важности | Сокращает количество рисуемых подписей в 5–20 раз |
| 5 | Сгруппировать подписи пространственно и переключать видимость групп | Пропускает целые области |
| 6 | Оставить `frustumCulled = true` и полагаться на отсечение three для мешей | Внеэкранная геометрия бесплатна |

## Вопрос 2 — рейкастинг с `InstancedMesh` / объединённой геометрией

Текущий прототип даёт каждому помещению собственный `Mesh`, потому что наведению и
выбору нужно состояние материала на помещение. При 1000+ помещениях это 1000 draw
call (карта теней строится один раз и кэшируется, поэтому больше не удваивает
стоимость) и 1000 целей рейкаста. `InstancedMesh` сворачивает всё это в **один**
draw call и **одну** цель рейкаста, но меняет способ адресации состояния на
помещение.

### `intersection.instanceId`

`Raycaster.intersectObject(instancedMesh)` возвращает пересечения с дополнительным
свойством:

```js
const raycaster = new THREE.Raycaster();
const pointer = new THREE.Vector2();          // NDC
raycaster.setFromCamera(pointer, camera);

const hits = raycaster.intersectObject(instancedMesh);   // НЕ intersectObjects(mesh.children)

for (const hit of hits) {
  const instanceId = hit.instanceId;           // 0 … count-1, или undefined
  if (instanceId === undefined) continue;       // попали в сам instanced mesh

  const shop = shops[instanceId];              // ваш инстанс -> таблица данных
  highlight(instanceId);
}
```

Ключевые моменты:

* `instanceId` — это **индекс инстанса в `InstancedMesh`**, то есть индекс слота
  в `instanceMatrix`. Для обычного меша он равен `undefined`.
* Точка попадания по-прежнему в **мировом пространстве** (`hit.point`), а
  `hit.face` относится к *общей* геометрии — не к геометрии отдельного инстанса.
* `hit.object` — сам `InstancedMesh`, поэтому вы должны сами сопоставить
  `instanceId` со своими данными. `Map<number, ShopData>` или обычный массив с
  индексацией по `instanceId` — естественная структура (см. вопрос 3).
* Рейкаст по `InstancedMesh` проверяет **общую** геометрию против каждого
  инстанса — тест луча/коробки выполняется для каждого инстанса в его локальном
  пространстве, поэтому это по-прежнему `O(instances)`. Это дешевле, чем N
  отдельных мешей, потому что отсечение по ограничивающей сфере общее, но не
  бесплатно.

### Работа с матрицей инстанса

У каждого инстанса есть собственное преобразование 4×4 внутри
`InstancedBufferAttribute` `instanceMatrix`. Чтобы переместить, масштабировать или
перекрасить один инстанс:

```js
import * as THREE from 'three';

const dummy = new THREE.Object3D();

function setInstanceTransform(mesh, index, x, y, z, sx = 1, sy = 1, sz = 1) {
  dummy.position.set(x, y, z);
  dummy.scale.set(sx, sy, sz);
  dummy.rotation.set(0, 0, 0);
  dummy.updateMatrix();                        // собираем TRS в Matrix4
  mesh.setMatrixAt(index, dummy.matrix);       // пишем в instanceMatrix
  mesh.instanceMatrix.needsUpdate = true;      // <-- загрузка на GPU
}
```

`setMatrixAt()` пишет в массив на стороне CPU; **`instanceMatrix.needsUpdate = true`
обязателен**, иначе GPU никогда не увидит изменение. (Альтернативно
`mesh.instanceMatrix.setUsage(THREE.DynamicDrawUsage)`, когда преобразования
меняются каждый кадр, чтобы three загружал весь буфер вместо диапазона.)

Чтение матрицы обратно:

```js
const matrix = new THREE.Matrix4();
mesh.getMatrixAt(index, matrix);
const position = new THREE.Vector3().setFromMatrixPosition(matrix);
```

### Цвет на инстанс и другие атрибуты

Цвет на инстанс встроен: `InstancedMesh.setColorAt(index, color)` пишет в атрибут
`instanceColor`, а `instanceColor.needsUpdate = true` загружает его. Материал
должен быть создан с включённым `vertexColors`, чтобы цвет дошёл до фрагментного
шейдера:

```js
const material = new THREE.MeshStandardMaterial({ color: 0xffffff, vertexColors: true });
mesh.setColorAt(index, new THREE.Color(shop.color));
mesh.instanceColor.needsUpdate = true;
```

Для всего остального (интенсивность эмиссии, флаг «выбрано», индекс текстуры в
атласе) вы добавляете собственный `InstancedBufferAttribute` в геометрию:

```js
const geometry = new THREE.BoxGeometry(1, 2, 1);

// один float на инстанс
const emissive = new THREE.InstancedBufferAttribute(new Float32Array(count), 1);
geometry.setAttribute('aEmissive', emissive);

// один vec2 на инстанс -> плитка атласа
const atlas = new THREE.InstancedBufferAttribute(new Float32Array(count * 2), 2);
geometry.setAttribute('aAtlas', atlas);

function setEmissive(mesh, index, value) {
  mesh.geometry.attributes.aEmissive.array[index] = value;
  mesh.geometry.attributes.aEmissive.needsUpdate = true;
}
```

и читаете его в модифицированном шейдере:

```js
material.onBeforeCompile = (shader) => {
  shader.vertexShader = shader.vertexShader
    .replace('#include <common>', '#include <common>\nattribute float aEmissive;\nvarying float vEmissive;')
    .replace('#include <begin_vertex>', '#include <begin_vertex>\nvEmissive = aEmissive;');
  shader.fragmentShader = shader.fragmentShader
    .replace('#include <common>', '#include <common>\nvarying float vEmissive;')
    .replace(
      '#include <emissivemap_fragment>',
      '#include <emissivemap_fragment>\ntotalEmissiveRadiance += vEmissive * diffuseColor.rgb;'
    );
};
```

**Важно:** обновлениям `InstancedBufferAttribute` тоже нужен `needsUpdate = true`,
причём для *всего* буфера. Если изменился только один инстанс, это всё равно
перезагружает весь атрибут — при 1000 инстансах это 4 КБ для float-атрибута, что
ничтожно.

### Стратегия подсветки с `InstancedMesh`

* **Наведение** — записать новый цвет в `instanceColor` для наведённого индекса и
  восстановить предыдущий. Две записи в буфер на событие наведения.
* **Выбор** — записать эмиссивный атрибут для выбранного индекса или использовать
  `setMatrixAt()`, чтобы слегка увеличить выбранный инстанс (1.04×), и отрисовать
  отдельный одиночный меш-контур, следующий за выбранным инстансом.
* **Не** клонировать `InstancedMesh` на каждый выбор — это убивает весь смысл.

### Объединённая (неинстансированная) геометрия

`BufferGeometryUtils.mergeGeometries()` создаёт одну `BufferGeometry` со всеми
запечёнными коробками. Рейкастер тогда сообщает `faceIndex` в объединённой
геометрии, и вы должны сопоставить его с помещением:

```js
import { mergeGeometries } from 'three/addons/utils/BufferGeometryUtils.js';

const merged = mergeGeometries(boxGeometries);   // один меш, один draw call

// Сопоставляем диапазон треугольников каждого помещения с его id.
const triangleToShop = new Uint16Array(merged.index.count / 3);
for (let i = 0; i < boxes.length; i++) {
  const start = merged.groups ? merged.groups[i].start / 3 : (i * 12);
  triangleToShop.fill(i, start, start + 12);      // коробка = 12 треугольников
}

raycaster.intersectObject(mergedMesh, (hit) => {
  const shopIndex = triangleToShop[hit.faceIndex];
});
```

**Компромисс:** объединённая геометрия — самая быстрая в отрисовке, но **худшая**
для взаимодействия: вы теряете цвет и преобразования на помещение и платите
`O(n)` поиском треугольник→id на каждое попадание. Для карты, где важны наведение
и выбор, `InstancedMesh` почти всегда лучше.

## Вопрос 3 — быстрые структуры поиска данных

Прототип отвечает на два очень разных вида запросов:

1. **«Дай мне помещение с таким id»** — поиск по идентичности, выполняется
   постоянно (события указателя, колбэки подписей, обновления DOM).
2. **«Что находится в этой мировой позиции?»** — пространственный поиск, нужен
   для определения по клику, для «перейти к ближайшему помещению» и для отсечения.

### `Map<string, ShopData>` для поиска по идентичности — O(1)

`Map` (или `Object`) даёт амортизированный **O(1)** поиск против **O(n)** у
`Array.prototype.find` / `Array.prototype.findIndex` по массиву из 100 элементов
(и 1000+ в масштабированном сценарии).

```js
// Строим один раз, сразу после генерации данных.
const shopById = new Map(shops.map((shop) => [shop.id, shop]));

shopById.get('shop_043');            // O(1) -> ShopData
shopById.has('shop_043');            // O(1)
shopById.set('shop_043', nextShop);  // O(1)
shopById.delete('shop_043');         // O(1)
shopById.size;                       // O(1)
```

Важные свойства:

* **Стабильный порядок итерации** — порядок вставки, поэтому итерация
  предсказуема (в отличие от обычного объекта, у которого тоже определён порядок
  для строковых ключей, но есть ловушки с унаследованными свойствами).
* **Никаких сюрпризов приведения к строке** — тип ключа сохраняется.
* **В отличие от `Object`**, `Map` не наследует от `Object.prototype`, поэтому
  такой id, как `"constructor"` или `"__proto__"`, не может столкнуться с членом
  прототипа.

Тот же подход применяется к **размещениям**:

```js
const placementById = new Map(placements.map((p) => [p.id, p]));
// -> { id, x, z, width, depth, shelf }
```

`main.js` хранит именно это (`placements`), а `interaction.js` держит вторую
карту от id к мешу:

```js
this.meshById = new Map(meshes.map((mesh) => [mesh.userData.shopId, mesh]));
```

так что наведение или выбор никогда не требуют поиска по массиву.

**Когда использовать массив вместо этого:** если ключ поиска — плотный целый
индекс (`instanceId` у `InstancedMesh`), обычный массив быстрее `Map` —
индекс *и есть* смещение, хеширование не участвует.

### Пространственный хеш-грид — O(1) на ячейку, O(k) результатов

Для «что находится в (x, z)?» классическое решение — **равномерный
пространственный хеш**: мир делится на квадратные ячейки со стороной `cellSize`, и
каждое помещение регистрируется в ячейках, которые оно перекрывает.

```js
class SpatialHash {
  constructor(cellSize) {
    this.cellSize = cellSize;
    this.cells = new Map();            // "cx,cz" -> ShopData[]
  }

  _key(cx, cz) {
    return `${cx},${cz}`;              // строковый ключ -> поиск в Map это O(1)
  }

  insert(item) {
    const half = item.width / 2;
    const halfD = item.depth / 2;
    const x0 = Math.floor((item.x - half) / this.cellSize);
    const x1 = Math.floor((item.x + half) / this.cellSize);
    const z0 = Math.floor((item.z - halfD) / this.cellSize);
    const z1 = Math.floor((item.z + halfD) / this.cellSize);

    // Помещение может занимать несколько ячеек: регистрируем его в каждой.
    for (let cx = x0; cx <= x1; cx++) {
      for (let cz = z0; cz <= z1; cz++) {
        const key = this._key(cx, cz);
        let bucket = this.cells.get(key);
        if (!bucket) this.cells.set(key, (bucket = []));
        bucket.push(item);
      }
    }
  }

  query(x, z) {
    const key = this._key(Math.floor(x / this.cellSize), Math.floor(z / this.cellSize));
    return this.cells.get(key) ?? [];
  }
}
```

* **Стоимость построения:** `O(n)` (каждое помещение вставляется в ячейки,
  которые покрывает).
* **Стоимость запроса:** `O(1)` на нахождение ячейки, `O(k)` для `k` помещений
  в ней — при размере ячейки, сопоставленном среднему размеру помещения, `k` —
  небольшая константа (1–4 помещения), поэтому запрос фактически **O(1)**.
* **Память:** один массив на занятую ячейку плюс строковые ключи. При `cellSize`
  ≈ средней ширине помещения 1000 помещений дают ~1000–1500 бакетов.

Чтобы сделать ключ дешевле, замените шаблонную строку числовым ключом:

```js
_key(cx, cz) { return (cx + 32768) * 65536 + (cz + 32768); }   // одно число
```

`Map` с числовыми ключами избегает аллокации строки на каждый запрос.

**Выбор размера ячейки:** `cellSize ≈ средней ширине помещения` даёт лучший
компромисс. Слишком мало → в большинстве ячеек по одному помещению, но карта
растёт; слишком много → в каждой ячейке много помещений и запрос деградирует до
линейного перебора.

### Квадродерево / октодерево — O(log N) при переменной плотности

**Квадродерево** рекурсивно делит мир на четыре квадранта, пока узел не будет
содержать меньше `capacity` помещений. Это правильный выбор, когда плотность
*очень* неравномерна (несколько огромных якорных арендаторов на почти пустом
этаже).

```js
class Quadtree {
  constructor(bounds, capacity = 8, depth = 0, maxDepth = 8) {
    this.bounds = bounds;              // { x, z, halfWidth, halfDepth }
    this.capacity = capacity;
    this.depth = depth;
    this.maxDepth = maxDepth;
    this.items = [];
    this.children = null;
  }

  insert(item) {
    if (this.children) {
      const child = this._childFor(item);
      if (child) return child.insert(item);
    }
    this.items.push(item);
    if (this.items.length > this.capacity && this.depth < this.maxDepth) this._split();
  }

  query(range, out = []) {            // range = { minX, maxX, minZ, maxZ }
    if (!this._intersects(range)) return out;
    for (const item of this.items) {
      if (range.minX <= item.x && item.x <= range.maxX &&
          range.minZ <= item.z && item.z <= range.maxZ) out.push(item);
    }
    if (this.children) for (const child of this.children) child.query(range, out);
    return out;
  }
}
```

* **Вставка:** `O(log N)` амортизированно.
* **Запрос:** `O(log N + k)` для точечного запроса, `O(log N + k)` для запроса
  по прямоугольнику.
* **Память:** один узел на разбиение — намного тяжелее хеш-грида.

### Что использовать здесь?

| Запрос | Структура | Сложность |
| --- | --- | --- |
| «помещение с id X» | `Map<string, ShopData>` | **O(1)** |
| «помещение в (x, z)» | Пространственный хеш-грид | **O(1)** + малый `k` |
| «помещения в прямоугольнике» | Пространственный хеш-грид (перебор покрытых ячеек) | O(ячеек + k) |
| «ближайшее помещение к (x, z)» | Пространственный хеш-грид, поиск расширяющимися кольцами | O(k) |
| «помещения в разреженном огромном мире» | Квадродерево | O(log N + k) |

Для этого торгового центра — ограниченного, плотного, примерно равномерного
этажа — **пространственный хеш-грид** и есть правильный ответ: O(1) на построение
для помещения, O(1) на точечный запрос, и ему не нужна рекурсивная структура.
Квадродерево окупается только когда мир неограничен или чрезвычайно разрежен.

### Замечание о рейкастере

`Raycaster` — это *геометрический* запрос, а не запрос по пространственной
структуре: он проверяет луч против ограничивающего объёма каждого кандидата (или
каждого инстанса). Для 100 помещений это тривиально; для 1000+ помещений
комбинируйте обе техники — используйте пространственный хеш, чтобы найти
несколько помещений рядом с указателем, и выполните точный рейкаст только по ним.
Это превращает `O(n)` рейкаст за кадр в `O(1)` поиск плюс несколько точных
тестов.

## Замечания по производительности

Прототип оптимизировали потому, что 3D-вид падал до **15 FPS** при движении
камеры. Каждое число ниже измерено, а не угадано — харнессы
`scripts/perf-*.mjs` есть в репозитории.

### Что было медленным и почему

| Проблема | Причина | Исправление |
| --- | --- | --- |
| Вся сцена рисовалась **дважды** каждый кадр | `renderer.shadowMap.autoUpdate` по умолчанию `true`, поэтому карта теней 2048² заново рендерилась для всех 103 объектов в каждом кадре | Сцена статична, поэтому карта теней строится **один раз**: `shadowMap.autoUpdate = false` + одноразовый `needsUpdate = true`. Размер карты также уменьшен до 1024². |
| ~9 мс кадра уходило на подписи | Запись `--label-width` (`max-width`) заставляет браузер **заново измерять текст**, чтобы найти позицию многоточия — для 100 элементов каждый кадр | Ширина и текст вычисляются в JavaScript и записываются **только когда реально меняются**; масштаб округляется до шага 0.05 |
| Полноэкранный прозрачный canvas-слой подписей | При DPR 2 это 3200 × 2000 прозрачных пикселей, которые каждый кадр нужно очистить, перерисовать и заново композитить поверх WebGL — на слабом GPU подписи стоили ~19 FPS против ~31 без них | Подписи перенесены в WebGL: спрайт с закэшированной `CanvasTexture` на магазин, отдельный ортографический проход, никакого второго полноэкранного слоя |
| `backdrop-filter: blur(3px)` на 100 подписях | Браузер должен читать и размывать **анимируемый WebGL-canvas** за каждой подписью каждый кадр | Удалено — фон подписи просто стал более непрозрачным |
| Вынужденная синхронная раскладка каждый кадр | `container.clientHeight` читался внутри цикла рендеринга сразу после записи подписей | Размер вьюпорта кэшируется и обновляется по `resize` |
| Подписи пересчитывались, даже когда камера стояла на месте | `labels.update()` выполнялся безусловно | `cameraChanged()` сравнивает матрицы камеры и пропускает всё обновление; сами матрицы сравниваются с допуском, чтобы шум вычислений не включал перерисовку |
| Кадр рисовался каждый `requestAnimationFrame` | Даже на неподвижной сцене WebGL очищал и рисовал тот же кадр, а подписи перерисовывались из-за субпиксельного дрожания камеры — это выглядело как мерцание | Цикл рисует кадр только при реальном изменении (камера, наведение, подписи, выбор, resize, смена разрешения); `OrbitControls.update()` откатывает позу, если сообщает об отсутствии изменений |

### Текущие числа

Измерено при вращении камеры (100 помещений, 1600 × 1000, тени включены):

| Метрика | До | После |
| --- | --- | --- |
| Draw calls за кадр | 206 (цвет **и** проход теней) | **106** (только проход цвета) |
| Треугольников за кадр | 2 404 | **1 204** |
| Рендеров карты теней за кадр | 1 (2048²) | **0** (построена один раз, 1024²) |
| Стоимость `labels.update()` (CPU) | 8.4 мс | **0.6 мс** |
| Время кадра, headless-софтверный рендерер | 145 мс | **40 мс** |

### Что ещё сделано

* 100 объектов контуров **объединены** в один `LineSegments`
  (`mergeGeometries`) — экономия 100 draw calls;
* рейкаст **ограничен** одним за кадр и полностью пропускается, когда указатель
  неподвижен;
* масштаб подписей задаётся размером спрайта, а не `font-size`/CSS-стилями —
  никакого reflow и пересчёта стилей;
* **динамическое разрешение**: если измеренная частота кадров падает ниже 40 FPS,
  сцена рендерится с меньшим соотношением пикселей (вплоть до 0.6×); как только
  появляется запас, полное разрешение восстанавливается. Это единственный
  механизм, гарантирующий плавную частоту кадров на слабом GPU — остальные
  оптимизации убирают работу, а этот адаптируется к тому, что осталось.

### Как воспроизвести измерения

```bash
npm run dev            # в одном терминале
npm run perf-check     # стоимость кадра при вращении
npm run perf-labels    # цена подписей в WebGL и отсутствие перерисовок в простое
npm run perf-experiment # стоимость каждой опции рендеринга
```

> **Примечание.** Харнессы управляют headless Chrome, который рендерит через
> SwiftShader (программная растеризация). Абсолютный FPS там намного ниже, чем
> на реальном GPU, и ограничен заполнением — поэтому относитесь к числам как к
> *относительным*. Количество draw calls, количество треугольников и тайминги
> `update` / `style+layout` на стороне CPU не зависят от железа и являются
> достоверной частью измерения.
